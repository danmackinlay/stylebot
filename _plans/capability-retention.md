# Capability retention under off-model SFT

**Status: opened 2026-08-28 in an unmerged worktree, nothing built; ported to
main 2026-09-10 under D98.** Prompted by
[*How to reduce capability degradation from off-model SFT*](https://www.lesswrong.com/posts/wBsEFfQFteHSWCtsv/how-to-reduce-capability-degradation-from-off-model-sft)
(LessWrong), **via Michael Clark / wassname** — the pointer is his, and it is
logged in the danbot writeup's "Incoming" list. The question it raises is one
this project has never measured, which is the reason to take it seriously; the
technique it proposes is one this project should be careful with, for a reason
the post itself does not have to worry about.

## What the post says

Off-model SFT — supervising on labels from a *different* model — degrades
capabilities, and prior work suggests it **suppresses** rather than removes
them. Blue-team experiment: strip backdoors from a backdoored Qwen3-30B-A3B
using llama-3.1-8B labels, measuring a Pareto curve of MATH-500 retention
against backdoor removal. Findings:

- **Reminder training wins**: after the off-model SFT, a *small* amount of SFT
  on data generated by the original model recovers capability without much
  re-introducing the bad behaviour. Appendix: it peaks at ~10 steps × batch 32 ≈
  **320 samples**, and more is not better.
- **Two-distribution training loses** — worse than baseline. That is putting
  on-model data behind a marker (`<alt_mode>` + prompt) hoping to preserve
  capability on that slice while training the behaviour out of the rest.
- Inoculation prompting (few-shot / multi-turn) was also tried; reminder
  training was the best of the set.
- Caveat the authors raise: on-policy data from the original model can
  re-transmit whatever you were trying to remove.

## Does the diagnosis apply here? Yes — more extremely than in the paper

Our corpus is as off-model as a corpus gets. The paper's teacher was a *weaker
model*; ours is **a human**. Every target is Dan's published prose, which no
checkpoint of Qwen3.5-9B could have produced. At the time of writing (2026-08),
4,140+ of ~4,600 pairs were synthetic on the slop side and human on the target
side.

And there are candidate symptoms already in [`findings.md`](findings.md), all of
which we have so far read as *data* problems:

- **Identity fallback at out-of-distribution length** — a 5.4KB chunk came back
  byte-identical. The model does not do the task badly; it silently stops. That
  is the most degradation-shaped failure we have.
- **Run 1 / run 3 deletions** — over-compression, an authorial aside deleted, a
  blockquote broken.
- **Anchor invention** — 2 outputs in run 4a, 5 in run 2, inventing a
  destination the input never named.
- **`〈MASKED_*〉` preservation** — `STYLE_SYSTEM` has always promised it, the
  corpus teaches it in **zero** target-side pairs (D33), and it has never been
  tested. This is pure instruction-following on an untrained shape.

Counterweight, and it is a strong one: each of the first three was diagnosed as
a corpus defect and mostly *fixed* by corpus surgery. None needed a capability
intervention. So the honest prior is "probably data again" — which is an
argument for measuring before building, not for ignoring it.

## Where the transfer breaks, and it matters

**The trade runs the opposite way.** The paper wants to *remove* a behaviour and
*keep* capability, so on-policy data from the original model is free: it pulls
back toward the base, which is where capability lives, and only mildly back
toward the backdoor. We want to *install* a behaviour and keep capability.
Pulling back toward the base is pulling back toward **slop**. "Recovers
capabilities without increasing the rate of bad behaviour much" translates here
to "recovers capabilities without un-Dan-ing it much" — a claim that has to be
measured, not inherited.

Second limit: their degradation mechanism is a student imitating a *weaker
model*. Ours is a model imitating a human it cannot match. Those may not be the
same failure, and the post gives no evidence that they are.

## What we already do that the paper's setting did not

Worth writing down so nobody re-derives it, and so the expected effect size
stays honest — our exposure is structurally lower than theirs:

- **LoRA rank 32, not full-weight fine-tuning.** The red team's model organism
  was FWFT. A rank-32 adapter has far less room to damage the base.
- **One epoch** (`num_epochs: 1` in every run manifest).
- **Completion-only masking** — `TrainOnWhat.ALL_ASSISTANT_MESSAGES`, so no
  gradient flows through the prompt.
- **A frozen, task-specific system prompt.** `STYLE_SYSTEM` is present verbatim
  in every training example and every inference call. That *is* inoculation
  prompting: the behaviour is elicited by a marker at train time and the same
  marker is present at test time. We are already doing the third technique in
  the post, by accident of D14.

## Action items

**1. Build the adherence probe (free, do first — it is the gate).**
The paper's capability metric was MATH-500. Ours cannot be: we do not want a
chatbot, we want a styler that keeps the four promises in its own system prompt.
So the probe is a fixed, small set of inputs exercising exactly those promises on
shapes the corpus under-covers, scored by **string checks, no judge, no key**:

| probe | promise under test | pass condition |
|---|---|---|
| chunk containing `〈MASKED_1〉` | "Preserve any 〈MASKED_*〉 tokens verbatim" | token present, unaltered |
| heading-less chunk | the `CONTEXT_DROPOUT` case | rewritten, not refused or prefixed |
| inline code / math / link | "Preserve all markdown structure verbatim" | spans byte-identical |
| already-Dan-shaped chunk | do-no-harm | not churned into something else |
| over-length chunk | the identity fallback | measure the rate, do not assume |
| any of the above | "Return only the rewritten prose, nothing else" | no preamble, no wrapper quotes |

Run it against **run 4a and the raw base model under the same system prompt**.
That comparison is the whole point: if the adapter adheres at least as well as
the base it was trained from, **there is no degradation and reminder training is
a solution to a problem we do not have**. Cost is sampling only.

**2. Reminder training (gated on 1 showing a gap).** ~320 samples, ~10 steps of
SFT on base-model-generated data, after the main run. Two blockers, one cheap:

- `run_training` **records** `result.checkpoints.state_path` but has no path to
  *consume* one — there is no resume-from-checkpoint. That plumbing does not
  exist and is the real cost of this item.
- Pre-register the acceptance rule before spending, or this becomes a fishing
  expedition: **adopt only if the probe improves AND detector / fit-judge /
  anchor damage do not regress.** The fit judge (D97) and its positive control
  are exactly the instrument for "did we un-Dan it", and they exist now.

**3. Log the negative result next to D33 (free, done with this file).**
Two-distribution training was *worse than baseline*. D33's planned masking
dropout — mask a fraction, leave `1 − p` unmasked so the styler does not
*require* the sentinel — is not the same construction, but "partition the input
distribution with a marker and hope capability survives on one side" is what it
looks like from a distance. Not a reason to abandon the dropout; a reason to
measure it rather than assume it is free.

## Inputs / outputs / done-criteria

**Inputs**: a promoted manifest (the adapter under test) + the same base model
with no adapter; `OPENROUTER_API_KEY` not required — Tinker sampling or the MLX
local build both serve. No corpus needed: the probe inputs are fixtures, and
should be **committed fixtures**, not sampled from the corpus, or the probe
drifts with the data it is supposed to be independent of.

**Outputs**: `adherence.jsonl` — one record per (probe, arm): the input id, the
output, and a boolean per promise; plus a summary with per-promise pass rates
for each arm.
